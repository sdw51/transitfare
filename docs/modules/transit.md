# transit 모듈

지역·운영사·역·노선·요금 데이터를 갖고, 구간 요금을 계산한다. 다른 모듈은 부르지 않는 말단 모듈.
패키지 `com.transitfare.transit`, DB 스키마 `transit`, 마이그레이션 `db/migration/transit`(V1~V99).

## 하는 일
- 지역·운영사·역 조회 (일정 입력 화면의 운영사 드롭다운, 역 자동완성)
- 구간 요금 계산 (요금 미리보기, 여행 요약, 경로 후보 요금)
- Google 경로 단계를 우리 역·노선으로 매칭 (경로 후보)
- 관리: 운영사 GTFS(쇼와 버스 등)에서 정류장·요금 가져오기

## 요금 계산 (domain)
`FareEngine`이 순서만 정하고 요금 방식별 계산기가 계산한다. 모든 금액은 어른 1명 기준(어린이 요금은 다루지 않음), `partyTotal = (base + express + reserved) × adults`.

1. **계산 단위로 자르기**(`FareUnit`): 같은 운영사 거리제 구간이 이어지면(사이 도보 포함) 한 묶음, 나머지는 구간 하나.
2. **방식별 계산**
   - `DistanceBandCalculator`(지하철·JR, `DISTANCE_BAND`): 묶음 첫 승차역~마지막 하차역 `pair_fare`가 있으면 그것(특정 구간 예외, 사용자 결정), 없으면 구간 km 합으로 거리 밴드. 특급요금도 같은 방식(특급 구간만). 지정석 요금은 지정석 구간마다. 금액은 묶음 첫 구간, 나머지는 0 + "앞 구간과 합산", 같은 `groupId`.
   - `StationPairCalculator`(`STATION_PAIR`): 역 쌍 요금 + 특급·지정석.
   - `FlatZonePlusPairCalculator`(니시테츠 버스, `FLAT_ZONE_PLUS_PAIR`): 같은 균일 구간이면 균일 요금, 아니면 쌍 요금.
   - `ManualFareCalculator`: 직접 입력 금액(`MANUAL`).
3. **환승 할인**(`TransferDiscountApplier`): 직전 운영사 → 다음 운영사 할인을 두 번째 구간 운임에서 뺀다(도보는 건너뛰고, 직접 입력이 끼면 끊고, 0원 아래로 안 내림).
4. **인원 곱하기.**

데이터에 없는 요금은 0원이 아니라 `UNKNOWN`(note에 빠진 항목). 거리제 묶음은 하나라도 모르면 묶음 전체 `UNKNOWN`.

## 역 매칭 (`matchStep`)
1. 운영사: `operator_alias.alias == agencyName`(정확히). 같은 별칭 운영사가 여럿이면(예: "西日本鉄道" = 니시테츠 전철·버스) 승차·하차역이 둘 다 있는 첫 운영사(코드 순).
2. 역: `name_ja`·별칭 정확 일치 → 없으면 `StationNameNormalizer`(공백·전각·끝의 "駅" 제거) 후 일치.
3. 노선: 두 역의 공통 노선(여럿이면 이름이 `lineName`과 겹치는 것, 그래도 여럿이면 id 순 첫 번째). 없으면 `lineId = null`.
4. 열차·노선 이름에 "特急" → `EXPRESS`.

에러를 던지지 않는다. 못 찾으면 빈 값 → directions가 그 구간을 `UNKNOWN`으로 두고 후보는 유지.

## GTFS 가져오기
`stops.txt` → `station`(같은 이름 승강장은 한 역, 이미 있는 역은 덮지 않음, `name_ko` 비움), `fare_rules.txt`의 `origin_id`·`destination_id`(구역) × `fare_attributes.txt` 가격 → `pair_fare`(BASE). 재실행은 멱등(금액·출처·확인 날짜만 갱신). 구역 방식 규칙(`contains_id`·`route_id`만)·요금 파일 없음은 `skipped`에 사유. 쇼와 버스 GTFS(CC BY 4.0)는 `backend/data/import/`(gitignore)에 둔다. 실제 가져오기는 Task I1.

## 테이블 (`transit.`)
| 테이블 | 내용 |
|---|---|
| `region` | 지역(코드, 이름, 통화, 시간대) |
| `operator` | 운영사(요금 방식 `fare_rule_type`, 요금 기준 설명 `fare_basis_note`) |
| `operator_alias` | 운영사 다른 이름(Google agency 이름) |
| `line`, `line_station` | 노선, 노선별 역과 누적 km |
| `station`, `station_alias` | 역(운영사별 행, 운영사 안 이름 유일), 역 다른 이름 |
| `distance_fare_band` | 거리 구간 요금(BASE·EXPRESS) |
| `pair_fare` | 역 쌍 요금(양방향 동일, BASE·EXPRESS) |
| `flat_zone`, `flat_zone_station` | 균일 구간과 그 정류장 |
| `reserved_seat_fee` | 지정석 요금(운영사당 하나) |
| `transfer_discount` | 회사 간 환승 할인(방향 있음) |

- id는 `generated by default as identity (start with 100000)`. 시드(V100~)는 id를 넣지 않고 이름 서브쿼리로 참조.
- 요금 금액 컬럼은 `amount` 하나(어른), 모든 요금 행에 `source_url`, `verified_on`.
- 마이그레이션: `V1__transit_schema`, `V2__transit_seed_region_operators`(지역 JP-FUKUOKA, 운영사 8개. 요금 기준 근거는 SQL 주석).

## 알려진 한계·다른 세션 참고
- **같은 이름 운영사:** 버스·전철 양쪽에 같은 이름 정류장이 둘 다 있으면 코드 순 첫 운영사로 정해져 틀릴 수 있다. Task 12에서 실제 Google 응답을 보고 문제가 되면 `StepToMatch.vehicleType` 추가(계약 변경)를 검토.
- **노선을 넘어 달리는 JR 직통 열차**(예: 특급 유후 博多→日田, 久留米에서 鹿児島本線→久大本線)는 공통 노선이 없어 요금이 "거리" 미확인이 된다. directions의 `ThroughServiceSplitter`가 경계역으로 나눠야 한다.
- **IC카드:** 모든 요금은 현금(종이 승차권) 기준이다(`fare_basis_note`). 니시테츠 버스 일부 노선의 IC·카드 할인, nimoca 환승 할인은 반영하지 않는다.
- **직접 입력 금액이 빠진 구간:** 400이 아니라 `UNKNOWN`(프론트 입력칸에서 막는다).
- **이 브랜치의 `docs/contracts.md`는 0단계 버전이다.** 최신은 메인 세션 `feat/enum-label`이고, 코드는 그쪽과 일치한다(`dev` 머지 때 맞춰짐).
