# 후쿠오카 대중교통 경비 계산기 — 설계

작성일: 2026-11-17

## 1. 의도와 이유

해외여행 전에 일정을 짜면서 **대중교통 총액**과 **가장 싸게 다니는 방법**(패스 vs 개별 요금)을 미리 계산하는 웹사이트.

- 첫 사용자는 만든 사람 본인. 다가오는 후쿠오카 여행 일정을 이 사이트로 계산하는 것이 첫 목표.
- 이후 다른 여행자도 쓰는 웹사이트로, 장기적으로 다른 도시로 확장 가능성.
- 성공 기준: 여행 전에 실제 일정(근교 이동, 특급열차 포함)을 입력해서 총액과 패스 추천을 신뢰할 수 있게 받는 것.

## 2. 목표 / 비목표 / 반목표

**목표**
- 날짜별 일정(구간 목록) 입력 → 구간 요금, 날짜별 합계, 여행 총액 계산
- 인원 입력(어른 수) → 1인 요금 × 인원
- 패스 비교: 패스를 쓰는 경우와 개별 요금을 비교해 가장 싼 조합 추천 (예: "3일째에 JR 북큐슈 패스 → ○○엔 절약")
- 같은 구간의 다른 이동 방법 비교 (예: 하카타→히타: 특급 / 보통열차 / 고속버스)
- 관리자 화면에서 역, 요금표, 추가요금, 패스, 역 이름 매칭을 수정 (요금 변경 시 코드 수정 없이 반영)

**비목표 (첫 버전)**
- 어린이 요금 (사용자 결정 2026-11-18: 전체에서 제외. 금액은 어른 1명 기준. 나중에 필드를 추가해서 넣을 수 있음)
- 배포 (로컬 실행으로 충분, 배포는 나중에)
- 자체 경로 탐색 엔진 (경로는 Google Routes에서 받음), 시간표 관리
- 아래 범위 밖 지역(나가사키·구마모토 등), 다른 도시
- 사용자 계정/로그인(관리자 인증 포함), 일정 공유
- 자전거 대여(공유자전거·렌터사이클)

**반목표 (동작해도 실패인 것)**
- 요금이 틀린 것. 총액이 틀리면 사이트의 의미가 없다. 확인 안 된 요금은 "미확인"으로 표시하고 조용히 추정치를 쓰지 않는다.
- 요금 변경 시 여러 곳을 고쳐야 하는 구조 (요금은 한 곳에서만 관리)
- 여행 전에 실제 일정 계산이 안 되는 것

## 3. 제약

- **무료.** 유료 API(NAVITIME, 駅すぱあと 등) 사용 안 함. Google Maps Platform은 SKU별 월 무료 한도(Essentials 10,000건, Pro 5,000건) 안에서 사용. 결제카드 등록 필요(사용자가 직접), 일일 사용량 상한 설정 권장.
- **공개 데이터 없음.** 조사 결과 니시테츠 버스·니시테츠 전철·JR 큐슈의 공개 GTFS/API 없음. 공공교통 오픈데이터센터(ODPT)에 후쿠오카·큐슈 기관 0곳. 후쿠오카 지하철은 시간표 엑셀만 공개(CC BY). 쇼와 버스는 GTFS 공개(CC BY 4.0). → 요금 데이터는 직접 입력·관리.
- **일정.** 2026-11-17 시작, **2026-11-23까지 전체 구현 완료** (사용자 결정). 여행은 그 이후.
- **기술(사용자 결정):** 백엔드 Spring Boot. 프론트엔드와 백엔드 분리.

## 4. 범위 (첫 버전)

**지역 (사용자 결정: 후쿠오카 출발 당일치기권으로 확장)**: 후쿠오카 시내(하카타 중심), 이토시마, 우키하, 히타(오이타현), 다자이후, 야나가와, 구루메, 무나카타, 가라쓰(사가현), 기타큐슈(고쿠라·모지코), 유후인·벳푸(오이타현).

**데이터 입력 순서**: ① 이번 여행 지역(시내·공항, 이토시마, 우키하, 히타) → 확인 → ② 다자이후·야나가와·구루메·무나카타·가라쓰 → ③ 기타큐슈 → ④ 유후인·벳푸. 아직 데이터가 없는 구간은 "미확인"으로 표시되므로 11/23까지 ①은 필수, ②~④는 가능한 만큼.

**교통수단**
- 후쿠오카 시영 지하철 (공항선·하코자키선·나나쿠마선)
- JR 큐슈: 지쿠히선(지하철 공항선 직통, 이토시마 방면), 가고시마 본선(하카타~구루메), 규다이 본선(구루메~우키하~히타), 특급(유후인노모리, 유후 등)
- 니시테츠 버스 (시내 주요 구간)
- 니시테츠 고속버스 "히타호" (후쿠오카~우키하~히타)
- 쇼와 버스 (이토시마·가라쓰 지역)
- 니시테츠 전철 (덴진오무타선·다자이후선: 다자이후, 구루메, 야나가와)
- JR 큐슈 추가: 가고시마 본선(무나카타·기타큐슈), 지쿠히선(가라쓰까지), 닛포 본선·규다이 본선(벳푸·유후인), 특급(소닉, 유후인노모리 등)
- 고속버스: 후쿠오카~기타큐슈, 후쿠오카~유후인·벳푸 등 (구체 노선은 조사 후 확정)
- 기타큐슈 모노레일 (필요 시)

**패스**: SUNQ 패스(북큐슈), JR 큐슈 레일패스(북큐슈), 후쿠오카 지하철 1일 승차권, 니시테츠 버스 1일 승차권, 후쿠오카 투어리스트 시티 패스, 다자이후·야나가와 관광 패스, 그 밖에 범위 내 지역 패스(조사 후 추가). 실제 적용 범위·가격은 데이터 입력 시 공식 자료로 확인.

> 노선·정차역·요금에 대한 이 문서의 서술은 대화 중 기억에 기반한 것이며, 데이터 입력 단계에서 반드시 공식 자료로 확인한다.

## 5. 검토한 접근법

### 5-1. 경로·요금 데이터를 어디서 얻나
| 방법 | 장점 | 단점 | 결과 |
|---|---|---|---|
| 구간 직접 입력만 (A) | 정확, 단순 | 길을 모르는 사용자에게 어려움 | 폴백으로 포함 |
| 자동 경로 탐색 — 유료 API | 유지보수 거의 없음 | 월 비용 | 무료 조건으로 탈락 |
| 자동 경로 탐색 — 공개 데이터 직접 구현 | 무료 | 니시테츠·JR 공개 데이터 없음 | 불가능 |
| Google Routes API의 요금을 그대로 사용 | 경로 커버리지 | 모든 구간 요금을 알 때만 총액 반환, 패스 정보 없음 | 탈락 (요금 신뢰성) |
| 주요 장소 간 대표 경로 + 요금 규칙 직접 관리 (C) | 무료, 정확 | 대표 경로를 직접 입력·관리해야 함, 등록 장소 밖은 불편 | 처음 선택했다가 아래로 교체 |
| **Google Places(장소 검색) + Google Routes(경로) + 요금은 자체 요금 규칙으로 계산 + 직접 입력 폴백** | 아무 장소나 입력 가능, 대표 경로 관리 불필요, 요금은 우리가 확인한 데이터라 정확 | Google Cloud 계정·결제카드 필요, Google 역 이름 ↔ 자체 역 데이터 매칭 필요, 약관(지도 표시·저장 제한) | **선택 (사용자 결정)** |

사용자의 우려(C안 당시): "경로를 다 입력해야 하고 요금 변경 유지보수가 어렵지 않나" → 경로에는 *무엇을 타는지*만 저장하고 요금은 별도 요금 규칙에서 계산하므로 요금 변경은 요금 규칙 한 곳 수정. 경로 수는 실제 여행 범위에서 수십 개 수준. 어떤 API를 쓰든 패스 적용 범위 데이터는 직접 관리해야 함.

### 5-2. 시스템 구조
| 방법 | 결과 |
|---|---|
| 서버 없는 정적 사이트 + 데이터 파일 | 제안했으나 사용자가 백엔드+프론트 구조 선택 |
| **백엔드 + DB + 관리자 화면 + 프론트, 로컬 실행 (배포는 나중)** | **선택 (사용자 결정)** |

## 6. 결정된 사항

### 사용자가 결정
- 여행 전 일정 계획용, 총액과 최저가 방법 둘 다 필요
- 버스·지하철·패스 모두 다룸
- 지역은 후쿠오카 출발 당일치기권(유후인·벳푸까지)으로 확장
- 특급열차 포함 (특급요금·지정석 요금 반영)
- 무료 운영
- 인원(어른 수)은 웹사이트에서 입력받음
- 백엔드 Spring Boot, 프론트·백엔드 모두 만들고 배포는 나중

### 설계자(Claude) 결정 — 수정 가능
- **백엔드**: Java + Spring Boot, Spring Data JPA. DB·빌드·아키텍처는 10-1장 참고.
- **프론트엔드**: React + TypeScript (Vite).
- **요금 계산은 전부 백엔드.** 프론트는 표시만.
- 데이터 구조는 GTFS/ODPT 개념(역·노선·요금 규칙)과 비슷하게 → 나중에 다른 도시로 확장 시 데이터 가져오기 쉽게.
- 숙소를 기본 출발/도착지로 설정하는 기능.
- **데이터 조사·입력 담당**: 빌더(Claude)가 공식 자료에서 요금·패스를 조사해 시드 데이터로 입력하고 출처 URL과 확인 날짜를 함께 기록. 사용자는 실제 일정 구간의 결과를 확인. 따라서 가장 먼저 완성할 것은 "시드 데이터 + 계산 + 사용자 화면"이고, 관리자 화면은 그 다음 우선순위.
- **일정 저장**: 일정(여행 설정 + 날짜별 구간)은 서버 DB에 저장해 새로고침해도 유지. 계정 없이 여러 일정을 목록으로 관리(첫 버전은 단일 사용자 전제). 공유 기능은 비목표 유지.
- **언어**: 화면은 한국어. 역·정류장·장소·패스는 일본어 공식명 + 한국어명 필드를 처음부터 둔다(공식 자료 대조와 향후 다국어 대비). 다국어 UI는 비목표.
- **일정은 고정하지 않음 (사용자 결정)**: 목적지는 사용자가 그때그때 웹사이트에서 입력. 첫 시드 데이터 범위는 이번 여행 지역(하카타·시내 주요 관광지·후쿠오카 공항, 이토시마, 우키하, 히타)이며, 테스트 케이스도 이 지역 구간으로 만든다.
- **데이터에 없는 구간의 폴백**: Google 경로의 역을 자체 데이터와 매칭하지 못하면 ① 사용자가 역/정류장을 직접 골라 요금 규칙으로 계산, ② 그것도 없으면 사용자가 요금을 직접 입력하는 "수동 구간"(운영사·메모·금액). 수동 구간은 계산에 포함하되 "직접 입력" 표시, 패스 커버 여부는 사용자가 운영사로 지정한 경우에만 판단.
- **할인 승차권 포함**: 왕복 할인권, 회수권(2매·4매 등)도 비교 대상. 패스와 할인 승차권을 "승차권 상품"이라는 하나의 개념으로 모델링(적용 구간, 가격, 사용 횟수/유효 기간).
- **요금 데이터 저장 방식**: 모든 역 쌍 요금을 저장하지 않고 계산 재료만 저장. 지하철 = 역별 누적 거리 + 거리 구간 요금표. JR = 노선별 역 누적 영업거리 + 거리별 운임표 + 거리별 특급요금표 + 예외(특정 구간) 요금표. 버스 = 균일 구간(정류장 목록 + 요금) + 필요한 정류장 쌍 요금만.
- **요금 데이터 입력 부담 (사용자 우려 반영)**: 사용자가 요금을 직접 입력하지 않는다. 빌더가 공식 자료로 조사해 시드 데이터로 넣고, 각 값에 출처 URL·확인 날짜를 남긴다. 공개 GTFS에 요금이 있는 운영사(쇼와 버스 등)는 가져오기 기능으로 자동 반영. 사용자는 실제 일정 구간의 계산 결과만 확인.
- **완성 목표일 (사용자 결정)**: **2026-11-23까지 전부 구현.** 여행 전 남는 기간은 실제 일정 입력·요금 확인에 사용.
- **우선순위**: 전부 11/23까지 구현 목표. 시간이 부족할 때만 뒤로 미루는 순서: 관리자 화면 → 인쇄용 요약 → 원화 환산 → Google 연동 (사용자: 원화 환산이 인쇄용 요약보다 중요)(없으면 역 직접 선택). 요금 데이터·요금 계산·일정 입력·승차권 비교는 반드시 먼저.
- **일행 이동 (사용자 결정)**: 일행은 항상 같이 움직인다. 인원은 여행 설정에서 한 번 입력하고 모든 구간에 동일 적용. 구간별 인원 변경·사람별 패스 계산은 하지 않음.
- **원화 환산 (사용자 결정)**: 여행 설정에 환율("1엔 = ○원")을 사용자가 직접 입력. 입력하면 모든 금액 옆에 원화 표시, 비어 있으면 엔화만 표시. 외부 환율 API는 나중에 추가 — 환율 기본값을 제공하는 부분을 분리해 두어 나중에 끼워 넣기 쉽게(설계자 결정).
- **승차권 상품 비교 범위 (설계자 결정)**: 등록된 모든 상품을 자동 비교. 사용자가 특정 상품을 비교에서 제외할 수 있는 토글 제공(예: 이용 자격이 없는 패스).
- **사용 환경 (사용자 결정)**: 여행 전 PC에서만 사용. 여행 전 배포 불필요, 데스크톱 화면 기준으로 설계(모바일 대응은 배포 시점에).
- **결과 가져가기 (설계자 결정)**: 일정 요약(날짜별 구간, 요금 내역, 총액, 추천 승차권)을 인쇄용 화면으로 제공 → 브라우저 인쇄로 PDF 저장해 여행 중 휴대폰에서 볼 수 있게. 별도 공유 기능은 없음.
- **대중교통 외 비용**: 자전거(공유자전거·렌터사이클)는 다루지 않음 (사용자 결정). 택시 등 그 밖의 비용이 필요하면 기존 "요금 직접 입력" 구간으로 넣을 수 있음(운영사 '기타', 승차권 비교 대상 아님 — 설계자 결정).
- **요금 정확성 확인 (설계자 결정)**: ① 요금 계산·승차권 비교는 공식 사이트에서 확인한 실제 구간 예시(하카타→텐진, 하카타→지쿠젠마에바루, 하카타→히타 특급 지정석, 히타호 등)로 자동 테스트. ② 사용자는 완성 후 실제 일정 몇 구간을 공식 사이트 요금과 대조.
- **승차권 상품 가격 (사용자 결정)**: 기본은 공식 가격(시드 데이터). 일정 설정에서 상품별로 "내 구매가"를 입력할 수 있고(엔화 또는 원화, 원화는 입력한 환율로 엔화 환산 — 환율 미입력 시 원화 구매가 입력 불가), 입력하면 비교·추천은 구매가로 계산. "비교에 포함" 토글과 같은 화면에 둔다.
- **패스 이용 자격**: 패스에 이용 조건(예: JR 큐슈 레일패스는 단기체류 외국인 전용) 필드를 두고 화면에 표시. 계산에서 제외하지는 않음.

## 7. Google 지도 연동 (사용자 결정: Google Maps Platform 사용)

흐름: **장소 검색(Google Places) → 경로 후보(Google Routes, 대중교통) → 각 경로의 탑승 구간을 자체 역 데이터와 매칭 → 자체 요금 규칙으로 요금 계산**. Google이 주는 요금(transitFare)은 사용자 화면에 표시하지 않는다(혼동 방지 — 설계자 결정). Google 요금은 구간별·특급/지정석 구분이 없고, 한 구간이라도 모르면 비어 오므로 계산에는 쓰지 않는다.

- **구간별 Google 요금으로 빈 구간 채우기 — 첫 버전 제외 (사용자 결정)**: 우리 데이터에 없는 구간을 Google에 구간 단위로 다시 물어 요금을 채우는 방식은 API 사용량 우려로 뺀다. 빈 구간은 "미확인" + 직접 입력. 나중에 추가할 수 있도록 구간 요금 출처를 분리해 둔다(설계자 결정). 다시 넣을 때의 안전장치 후보: 우리 데이터에 없는 구간만, 후보를 펼칠 때만 요청, 서버 일일 한도, 켜기/끄기 설정.
- **요금 검증 (사용자 결정)**: Google이 경로 요금(transitFare)을 준 경우, 같은 경로를 자체 요금 규칙으로 계산한 값(어른 1명, Google 요금과 같은 조건 — 특급 요금 포함 여부 등은 경로 정보로 맞춤)과 비교해 저장. 차이가 있으면 관리자 화면 "요금 불일치" 목록에 경로·두 금액·차이·발생 일시를 표시해, 요금 인상이나 데이터 입력 오류를 찾는 데 쓴다. 사용자 화면에는 노출하지 않음. 비교 기준(허용 오차, IC/현금 차이 처리)은 빌더가 정함.

- **경로 후보 여러 개**: Routes API에 대안 경로를 요청해 여러 후보를 받고, 각 후보를 자체 요금으로 계산해 비교 표시. 사용자가 후보 중 하나를 선택해 일정에 넣는다. (Google 추천 경로가 최저가가 아닐 수 있음.)
- **역 매칭**: Google 경로의 각 탑승 구간(노선명, 운영사명, 승차/하차 정류장명·좌표)을 자체 역/정류장과 연결. 자체 데이터에 Google 이름 별칭(alias) 필드를 둔다. 매칭 실패 구간은 "미확인"으로 표시하고 폴백(역 직접 선택 / 요금 직접 입력)으로 처리. 매칭 실패 로그를 남겨 관리자 화면에서 별칭을 추가할 수 있게 한다.
- **특급 판별**: Google 경로의 열차 종별 정보로 특급 여부를 추정하되, 사용자가 구간에서 "특급/보통", "지정석/자유석"을 바꿀 수 있게 한다.
- **API 키 관리**: Routes API 호출은 백엔드에서(서버 전용 키, 환경변수). 장소 자동완성과 지도 표시는 프론트에서 Maps JavaScript API로(HTTP referrer 제한 키). 키는 저장소에 커밋하지 않는다.
- **약관 준수**: Google 결과를 보여주는 화면에 Google 지도와 표기를 함께 표시. 일정에는 Google place ID, 장소 표시명, 매칭된 자체 역 ID만 저장(좌표 장기 저장 안 함).
- **비용**: SKU별 월 무료 한도 안에서 사용(Places Essentials 10,000건, Routes 10,000 또는 5,000건, Dynamic Maps 10,000건). 구현 전에 대중교통 경로 SKU 등급과 정확한 한도를 공식 문서로 확인. Google Cloud 계정 생성, 결제카드 등록, API 키 발급, 일일 사용량 상한 설정은 사용자가 직접(빌더가 안내).
- **API 키가 아직 없을 때**: 개발 초기에는 Google 응답을 흉내 낸 고정 데이터로 개발·테스트할 수 있게 경로 제공자를 인터페이스로 분리(설계자 결정).

## 7-1. 요금 모델

요금 규칙을 운영사(사업자)별로 둔다.

| 운영사 | 규칙 유형 | 내용 |
|---|---|---|
| 후쿠오카 지하철 | 거리 구간제 | 역별 누적 거리(km) + 거리 구간별 요금. 지하철 내 노선 환승은 전체 거리로 1회 계산 |
| JR 큐슈 | 영업거리 기반 운임 + 추가요금 | 노선별 역 누적 영업거리 → 거리별 운임표(노선 갈아타면 거리 합산). 특정 구간 예외 요금표 우선. 특급요금(거리별 표)·지정석 요금은 별도 항목으로 가산 |
| 니시테츠 버스 | 균일 구간 + 정류장 간 요금표 | 도심 균일 구간 내 고정 요금, 그 외 정류장 쌍별 요금. 승차마다 별도 계산 |
| 고속버스 히타호, 쇼와 버스 | 정류장 간 요금표 | 정류장 쌍별 요금 |

- **회사 간 환승**: 각 구간 요금 합산.
- **지하철↔JR 지쿠히선 직통**: 같은 열차라도 지하철 구간 요금 + JR 구간 요금 합산 (경계역 기준, 확인 필요).
- **환승 할인 규칙표**: "A→B 환승 시 ○엔 할인" 같은 예외를 별도 테이블로. 해당 할인이 확인되지 않으면 비워둔다.
- **어린이 요금**: 다루지 않는다(비목표). 모든 금액은 어른 1명 기준.
- **현금 vs IC카드**: 첫 버전은 한 가지(확인된 요금 기준)로 통일하고 어느 기준인지 화면에 표시. (설계자 결정)
- **미확인 요금**: 데이터에 요금이 없으면 계산을 0으로 하지 않고 "미확인" 표시, 총액에 "미확인 구간 포함" 경고.

## 8. 패스·할인 승차권 비교

(패스와 할인 승차권은 "승차권 상품"으로 통합. 아래 "패스"는 승차권 상품 전체를 뜻함. 할인 승차권은 기간 대신 적용 구간과 사용 횟수로 커버.)

- 패스 데이터: 이름, 가격(어른), 유효 기간(1일/2일/3일 등, 연속일 여부), 적용 운영사·노선·구간, 특급 포함 여부, 지정석 포함/횟수 제한 등.
- 계산: 여행 기간 전체에서 각 날짜(또는 연속 날짜 묶음)에 각 패스를 적용했을 때, 그 패스가 커버하는 구간 요금을 0으로 보고 패스 가격을 더해 총액을 비교. 가장 싼 조합과 절약액을 보여준다.
- 인원수만큼 계산 (패스 가격 × 인원).

## 10-1. 아키텍처 (사용자 결정, 구현 계획 단계에서 추가)
- **모듈러 모놀리스**: 서버 하나, MSA는 쓰지 않음(과함). 나중에 경계를 따라 분리 가능하게.
- **기능별 모듈** (`transit`, `pass`, `itinerary`, `directions`) 안에서 다시 나눈다. 모듈 이름은 `transit`(대중교통 데이터·요금 계산), `pass`(패스·할인 승차권), `itinerary`(여행·일정), `directions`(길찾기)(사용자 결정).
- **퍼사드 + 유스케이스**: 각 핵심 모듈은 `XxxFacade`가 유일한 공개 진입점. 다른 모듈은 퍼사드만 호출하고 엔티티·리포지토리를 직접 쓰지 않는다. 퍼사드 안쪽은 사용자 행동 하나당 유스케이스 클래스 하나(클린 아키텍처). 계산 로직은 `domain`에 순수 Java로.
- 관리자 CRUD는 단순하게(컨트롤러 → 리포지토리), 유스케이스로 쪼개지 않음.
- **빌드 (사용자 결정)**: Gradle Kotlin DSL(wrapper), Java 25, Spring Boot 4.x 최신 안정판.
- **MSA를 염두에 둔 모듈러 모놀리스 (사용자 결정)**: 다른 해외 지역을 많이 추가할 계획이므로 나중에 모듈을 서비스로 분리할 수 있게 만든다.
  - **모듈별 DB 스키마 분리**: `transit`(역·운영사·요금 데이터), `pass`, `itinerary`, `directions` 스키마. 다른 모듈 스키마의 테이블을 JOIN·FK로 참조하지 않고, 필요한 정보는 퍼사드로 받는다. 모듈 간에는 ID 값만 저장(FK 제약 없음).
  - **지역 개념**: `region(code, name_ko, name_ja, currency, timezone)`. 운영사·역·승차권 상품에 `region_code`. 여행은 지역 하나를 선택(첫 버전 선택지는 `JP-FUKUOKA`뿐). 금액은 지역 통화의 정수 최소 단위로 저장. 원화 환산은 "현지 통화 1단위 = ○원"으로 일반화(설계 6장의 환율 입력과 내 구매가 원화 환산에 동일 적용). 다른 지역 데이터·화면은 범위 밖, 구조만.
- **DB (사용자 결정)**: 개발·테스트는 **H2**(파일 모드 / 테스트는 메모리, `MODE=PostgreSQL`)로 Docker 없이 빠르게. H2도 스키마를 지원하므로 모듈별 스키마 분리를 그대로 적용. 운영(배포 시)은 PostgreSQL. 마이그레이션 SQL은 H2와 PostgreSQL 양쪽에서 동작하는 문법만 사용하고, `prod` 프로필(로컬에서는 Docker Compose의 PostgreSQL에 연결)로 가끔 실제 PostgreSQL에서 마이그레이션·테스트를 돌려 호환성 확인(설계자 결정). 설정 파일은 `application.yml`(공통) + `application-dev.yml`(H2, 기본 프로필) + `application-prod.yml`(PostgreSQL, 접속 정보는 환경변수)(사용자 결정).
- **API (사용자 결정)**: REST + JSON, 모든 경로에 버전 접두사 `/api/v1/...`. springdoc-openapi로 API 문서 자동 생성(Swagger UI `/swagger-ui`).
- **프론트엔드 (사용자 결정)**: React + TypeScript + Vite, React Router, TanStack Query, Vitest + Testing Library, UI는 **Mantine**. 표시 스타일: 열차 종별·좌석·소요시간 등 부가 정보는 배지가 아니라 **보조 텍스트**(작은 회색 글, 예: "지정석 · 1시간 40분")로. 단, "미확인" 같은 경고는 눈에 띄어야 하므로 경고색 텍스트로 표시(설계자 결정).
- **화면 디자인 (사용자 결정)**: 프론트엔드 화면 작업은 `frontend-design` 스킬을 사용해 디자인 방향(색, 글꼴, 레이아웃)을 정한다. Mantine은 부품 기반으로 쓰고, 그 방향에 맞춰 Mantine 테마(`createTheme`)를 맞춘다. 구현 계획은 화면의 기능·데이터·동작만 정하고 시각 디자인 세부는 스킬에 맡긴다.
- **테스트 (사용자 결정 + 설계자 구성)**: 요금 엔진·승차권 최적화(domain)는 TDD 단위 테스트, 실제 요금 골든 테스트, 유스케이스 통합 테스트(H2), ArchUnit 모듈 경계 테스트, API는 MockMvc 주요 케이스, 화면은 Vitest로 핵심 부품만. **E2E(Playwright)는 이번에 넣지 않고 배포 시 추가**, 전체 흐름은 수동 확인.
- **데이터 관리**: Flyway SQL 마이그레이션으로 스키마와 시드 데이터를 버전 관리(모듈별 마이그레이션 폴더).
- 모듈 경계 규칙은 테스트(ArchUnit 등)로 강제 — 빌더가 도구 선택.
